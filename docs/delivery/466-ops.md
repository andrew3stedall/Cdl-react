# #466 Operations and verification lane

This execution record covers #475, #476, and the operations slice of #531 on
`milestone/466-ops`. It includes source, CI, and hosted rollout evidence. Hosted
changes were made only by the existing user-authorized staging workflows; this
record does not claim a live recovery proof.

## Changes

- Runtime images install frontend packages with `npm ci` from
  `frontend/package-lock.json` and Python packages with `uv sync --frozen`
  from `uv.lock`. CI uses `npm ci` and `uv sync --locked`.
- A runtime Cloud Run revision is staged while the last healthy revision keeps
  100% traffic. The migration job image must match the immutable application
  image. Alembic upgrades to the checked-in head and then reads PostgreSQL's
  recorded heads back; a mismatch or migration error blocks promotion.
- Auto rollout, reviewed Terraform runtime apply, and direct fallback share the
  revision pin, migration, no-traffic readiness/auth-boundary smoke, then
  traffic-promotion sequence. The smoke URL comes from a unique temporary
  Cloud Run traffic tag read back from the Service's traffic-status entry;
  the tag is checked against the exact staged revision and the previous
  revision must retain 100% traffic. Cleanup removes the tag on success and
  failure without promoting traffic. The direct fallback keeps a failed
  migration from reaching the image-update step.
- The PostgreSQL release journey authenticates two managers through real DB
  sessions, creates and accepts a targeted invite, round-trips a lineup and
  chip state, and checks manager isolation. The Playwright smoke uses current
  20-player / five-chip browser fixtures at mobile and desktop widths and
  asserts interaction and overflow invariants. It collects no screenshots.

The deployment does not rely on a revision `status.url` field. It uses
`gcloud run services update-traffic --update-tags=...` to obtain a tagged
revision URL without changing serving percentages, then verifies the tagged
target and preserved live traffic before the smoke requests. Tag assignment
uses the documented Cloud Run Service traffic-target URL; a missing URL,
wrong target, or changed serving revision fails closed.

## Hosted runtime correction

The first postmerge Cloud Run migration job invoked system Python, while uv installed the app into `/app/.venv`. It failed before Alembic and promotion was blocked. Docker now puts the project environment first in PATH and imports `cdl_api.migrate` during image build, so the same `python -m` job command uses the installed project. The failed exact plan changed four existing image resources with no creates/destroys. Hosted follow-up must prove migration head, tagged candidate smoke, named promotion and FPL refresh before deployment is reported complete.

CI now builds the production runtime image and invokes its default `python` as the non-root runtime user to import both migration and FPL-refresh modules and check the virtual-environment interpreter. This catches the hosted job packaging failure before merge without contacting or mutating a database.


## Corrective rollout investigation

The initial postmerge rollout at main commit `f1d217f` stopped before Alembic
because system Python could not import `cdl_api`; no traffic promotion ran.
The follow-up runtime image fix at `0bb957e` passed its production-image import
check. Its automatic staging run `37129346428` applied four in-place Terraform
updates (zero adds, zero destroys), passed the post-apply no-change plan, and
completed migration execution `cdl-react-staging-db-migrate-v5dkn`. Revision
verification then failed because Cloud Run's latest created revision was not
reported as its latest ready revision. The workflow did not tag or promote a
candidate; the recorded serving revision remained `cdl-react-staging-api-00318-pl9`.
Health/auth smoke, FPL refresh, and post-promotion checks did not run.

The automatic failure triggered direct fallback run `37129534523`. It reported
`cdl-react-staging-api-00318-pl9` serving 100% after its database-attachment
repair step, then failed before migrations because the workflow had not checked
out the helper script it invokes. This lane records both failures as operational
evidence; neither is a successful hosted release. The next verification patch
adds a checkout, captures and protects the prior serving revision during repair,
waits only while Cloud Run reports a not-yet-ready revision, and keeps the
created/ready/image/traffic invariants fail-closed. Failure artifacts are
restricted to safe revision metadata and sanitized startup exception classes
and in-app stack frames; raw service JSON and raw logs are not uploaded.
